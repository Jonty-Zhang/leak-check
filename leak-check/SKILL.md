# leak-check：查雷，只出报告

一句话：**找出交上去会被老师一眼看穿或一眼看出不对的句子，列成清单，一个字都不改。**

姊妹 skill `leak-fix` 查完会直接修。两者共用 `scripts/` 和 `references/`。

## 查什么（v1）

- **雷点**：元话语（转述用户、老师、题目的要求）、草稿残留（之后要替换、待补充、TODO、【此处……】、XXX）、版本标记（改进版、最终版、修改前/修改后）、对话残留（好的，以下是……、希望对你有帮助）、AI 自曝、Markdown/LaTeX 残留、Word 批注、修订、高亮。
- **硬伤**：图表编号断裂或重复、正文引用了不存在的图表、文献编号超出文献表或不连续、"错误！未找到引用源"、标题编号跳号、空章节、重复段落、括号或引号不配对、前后数字矛盾、编造迹象明显的文献、结论和正文对不上、残句。
- **不查**：AI 味用词和套话（v2 再做，现在需要就用 `humanizer-zh`），以及排版（用 `word-report` / `word-format`）。

完整清单和每一类的例外见 `references/patterns.md`，**动手前必须读**。

## 流程

1. **确定要查的对象。** 用户给了文件就查文件；查的是对话里刚写的文本，就先存成临时 `.md` 再查。PDF 如果是扫描件（`--dump` 几乎没有文字），告诉用户脚本读不到，只能逐页看图。

2. **跑脚本**（`<本 skill 目录>` 就是加载时给出的 Base directory）：
   ```bash
   python3 <本 skill 目录>/scripts/scan_leaks.py 文件.docx
   python3 <本 skill 目录>/scripts/scan_leaks.py 文件.docx --dump    # 带段号的全文，用来通读
   ```
   多个文件可以一起传。输出很长时加 `--json`。

3. **通读全文。** 按 `references/semantic-checklist.md`（**必须读**）把 `--dump` 的输出从头读到尾，找脚本漏掉的变体和语义硬伤。同时逐条判断脚本报的问题：
   - **WARN**：每条都要定性，要么是问题，要么排除。
   - **ERROR**：也要看一眼上下文。出现在引文、代码，或者讨论 AI 的论文里的命中，按误报排除。

4. **出报告**，格式固定：

   ```markdown
   ## 查雷报告：文件名

   **结论**：N 处必须改，M 处建议看看。（脚本 ERROR a 条 / WARN b 条；通读新发现 c 条；排除误报 d 条）

   ### 必须改
   | # | 位置 | 原句 | 问题 | 建议改法 |
   |---|---|---|---|---|
   | 1 | 第 7 段 | 根据用户的要求，本文采用问卷法 | 转述用户要求 | 删去"根据用户的要求，"→"本文采用问卷法" |

   ### 建议看看
   （同上表格；写清楚为什么拿不准）

   ### 已排除
   - 第 12 段"用户希望按价格筛选"：需求分析里的用户是研究对象，属正常用法

   ### 没查的
   - （例如：图片里的文字没逐张看；文献真实性没联网核验）
   ```

   - "位置"用脚本的段号、行号，方便用户在 Word 里定位，也方便 leak-fix 接着修。
   - "原句"只截有问题的那一句，不贴整段。
   - "建议改法"写出改完的样子，不要只写"建议修改"。
   - 缺内容的（比如"此处插入流程图"），改法写"补上 X"，并说明缺的是什么。不要编一个内容填进去。
   - 同一类问题多处出现时合并成一行，列出全部位置。

5. **不改任何文件。** 报告最后用一句话提示：要直接修可以用 `/leak-fix`。

## 判断原则

- 唯一的标准：**这句话出现在交给老师的成品里，读者会不会觉得"这是 AI 写的"或者"这里没写完、写错了"？**
- 能从文档本身确认的（比如编号、前后数字）就直接下结论；确认不了的放进"建议看看"，并写明需要什么信息才能确认。
- 没查到问题，就如实写"没查到"，同时列出"没查的"范围。不要为了显得认真而凑问题。
